# LLM export改善計画（2026-10-08）

目的は、Gemini Notebook / NotebookLMなどにコードベースの根拠を正確に渡すこと。以下では実装済みの形式対応と、今後の設定・梱包方式の提案を区別する。

## 実装済み

OKF v0.2のルート目次、概念文書、生成情報、入力元情報、Markdownリンクに対応した。詳細は [出力仕様](detailed/export-format.md)。Docker内でYAML解析・実ZIP・ブラウザ操作を検証する。外部LLMへのアップロードと回答精度評価は未実施。

## 分割設定の方針（提案・未実装）

[公式FAQ](https://support.google.com/gemininotebook/answer/16269187?hl=en)の制限は1ソース50万語、アップロードファイル200MB。語数とバイト数は別の制約なので容量検証を削除しない。制限は変更され得るため、サービスプロファイルに確認日と出典を持たせる。

| 項目 | 通常UI | 残す理由・用途 |
|---|---|---|
| 出力先 | Gemini Notebook等のプリセット | 語数・容量・アップロード可能な形式をまとめて適用 |
| 目標語数 | 可変にする | ソース選択の粒度、更新範囲、ソース数との調整。45万語は上限寄りの初期案で、精度最適値ではない |
| 容量 | 上限検証を自動適用、任意指定は詳細設定 | 空白が少ない巨大データ、別サービスの容量制限、端末メモリへの配慮 |
| パート内ファイル数 | 既定は無制限、必要なら詳細設定 | 人間のレビューや更新単位を小さくしたい場合。関連性を表す指標としては弱い |
| 50万語の上限 | 対象サービスの固定上限として表示 | 通常プリセットで引き上げない。別サービス用カスタムプロファイルでは変更可能 |
| 入力ソース数 | 予測値と超過表示 | 元ファイル件数ではなく、アップロードする出力文書数で数える |

通常画面は「出力先・目標語数・まとめ方」に絞る。語数はローカル推定なので、50万ちょうどを狙わず余裕を確保する。トークン上限を使う別サービスでは語数とトークン数を混同しない。

[公式ソースガイド](https://support.google.com/gemininotebook/answer/16215270?hl=en)では無料枠は50ソース。概要・本文・必要な明細を合わせた入力数をプレビューする。ソース上限はプランで異なるため調整可能にする。小分けにしすぎても扱いにくくなる。OKFの構造だけで検索精度が向上すると断定しない。

## 優先順位と完了条件

### P1: 入力範囲を明示し、取りこぼしを減らす

現行の拡張子セットは `.go` / `.rs` などや `Dockerfile` / `Makefile` / `go.mod` などを既定で拾わない。既定1MiB超の単一ファイルも除外する。コード全体を理解する目的では重要な欠落になり得る。

- 代表的なソース言語・拡張子のないビルド定義を対象化し、依存物・生成物・バイナリの分類と区別する。
- 単一ファイルの「除外上限」と「分割上限」を分け、読める大きなソースは分割出力する。読み込み予算を超える場合は理由を表示する。
- プレビューに成功見込み・除外・失敗・未分類と代表パスを表示する。出力レポートから原因を追えるようにする。
- 完了条件: Go/Rust、拡張子なしファイル、大きいソース、生成物を含むfixtureで期待する収録集合と一致する。

### P2: 設定整理と関連性に沿った梱包

- 上記のプリセットと目標語数を導入し、保存済みの容量・件数設定は詳細設定へ移行する。
- モジュール／ディレクトリを基本単位に、対応するREADME・実装・テスト・設定をできるだけ同じパートにする。ファイル種別だけによる並び順で関連性を崩さない。
- 単一ファイル分割時は行境界を維持し、将来は言語パーサーで関数・クラス境界を優先する。巨大な1行は例外処理し、継続断片を明示する。
- 完了条件: 完成出力の上限遵守、Unicode本文の完全復元、旧設定移行、ソース数予測をDockerで確認する。

### P3: 根拠・関係・更新を追跡できるようにする

- 断片に元ファイルの行範囲、ファイルハッシュ、安定した識別子を付ける。Git commitは実際に取得できた場合のみ記録する。
- import/include、ビルド依存、公開API、対応テストを根拠付きで索引化する。解析できない動的参照は不明として残し、正規表現だけで完全な呼び出しグラフと称さない。
- モジュール単位の安定したパート名とマニフェストを導入し、変更のないソースを再アップロードしなくて済むようにする。
- 完了条件: fixtureの参照先・行範囲が一致し、単一モジュールの変更で他モジュールの名前が連鎖変更しない。

### P4: 回答精度を評価する

起動経路、設定の優先順位、モジュール間処理、変更影響、関連テストを問う10〜20問の評価セットを作る。正解の元パス・該当コードを用意し、語数目標と梱包方式を比較する。回答の正しさ、根拠の一致、欠落、入力数・更新負担を記録する。サービス側の検索方法にも依存するため、形式適合試験と回答精度評価を分ける。
